# Changelog

All notable changes to this project are documented in this file.
The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

Remote access on existing installs is unaffected unless they opt in. Two security changes apply to every install: login throttling and stricter permissions on `config.php` (see Changed). Re-running `python3 setup.py` on an existing install adds one question (the remote access mode, defaulting to port forwarding), an optional hostname allowlist question (defaulting to off) and a one-time question about automatic security updates (defaulting to yes; answering no changes nothing).

### Added
- Remote access modes in the setup wizard: None (LAN only, the default for new installs), Port forwarding (the previous behavior, the default for existing installs) and Cloudflare Tunnel. Re-running the wizard switches modes.
- Cloudflare Tunnel support. The wizard installs `cloudflared` from Cloudflare's apt repository and runs it as the `rwsols-cloudflared` systemd service. The tunnel token is kept in a root-only (0600) environment file, `/etc/cloudflared/rwsols-tunnel.env`, instead of being passed on the command line. `cloudflared` forwards to a loopback-only Apache virtual host (`rwsols-tunnel`, default 127.0.0.1:8080); the LAN listener is not changed.
- Automatic tunnel provisioning through the Cloudflare API (tunnel, ingress rules, proxied CNAME record), and a manual path that takes a tunnel token created in the Cloudflare dashboard. Provisioning is idempotent. Other ingress rules on an existing tunnel are kept, and a conflicting DNS record is shown and left alone unless `--force` is given.
- Optional Cloudflare Access for the tunnel hostname: automatic creation of a self-hosted Access application with an Allow policy (emails and/or an email domain), an optional service token for non-browser clients, or manual entry of the team domain and AUD tag. The automatic setup asks how long a login lasts (1 day, 1 week or 1 month; default 1 month) and applies it to the application and its policies; re-running the wizard changes it.
- Hostname allowlist (`$ALLOWED_HOSTS`, `$ALLOW_LOCALHOST`, `$LOG_HOST_REJECTIONS`) enforced by a generated Apache configuration (`/etc/apache2/conf-available/rwsols-allowed-hosts.conf`) and again in PHP. Rejected requests get an empty HTTP 421.
- New `config.php` settings: `$ALLOWED_HOSTS`, `$ALLOW_LOCALHOST`, `$LOG_HOST_REJECTIONS`, `$TUNNEL_HOSTNAME`, `$TUNNEL_ORIGIN_BIND`, `$TUNNEL_ORIGIN_PORT`, `$ACCESS_TEAM_DOMAIN`, `$ACCESS_AUD`. All optional.
- Setup script options: `--remote-access`, `--remove-tunnel`, `--dry-run` and `--force`. The Cloudflare API token is read from `CLOUDFLARE_API_TOKEN` or a hidden prompt and kept in memory only.
- `--remove-tunnel` (also offered when switching away from Tunnel mode) removes what the wizard created, as recorded in `.rwsols_remote_access.json`, and lists what it left alone.
- PHP and Python test suites (`tests/php`, `tests/python`).
- Reworked setup wizard interface. Every question, including the older steps in `setup.py`, now goes through one UI layer (`rwsols_setup/ui.py`) with short explanation boxes before the questions, a results checklist for the tunnel verification and a closing summary. It uses `rich` when it is installed and the terminal is interactive; the script tries `sudo apt-get install -y python3-rich` once at startup (skipped for `--help`, `--dry-run` and non-interactive runs, never uses pip) and silently falls back to plain text prompts, which also work with piped input.
- The hostname allowlist question is now a multi-select with a reason next to every candidate name (tunnel hostname, `<hostname>.local`, the router's reverse DNS name, LAN IP, names already on your list, dynamic DNS names). Type numbers to tick or untick, `a` to add your own name, Enter to accept. The tunnel hostname is required in Tunnel mode.
- The wizard suggests the router's local DNS name for the Pi (reverse lookup of its LAN IP) when it forward-resolves back to the same IP. It also tries `<hostname>.<DNS search domain>`. Names in a local DNS zone that neither lookup reveals have to be added by hand (`a` in the list).
- Tunnel mode suggests `rwsols.<first ddclient name>` as the tunnel hostname when ddclient is configured, and explains why a dedicated subdomain is recommended and that dynamic DNS keeps working next to the tunnel.
- Arrow-key selection in the wizard when `rich` is in use on a Linux terminal: Up/Down to move, Space to tick or untick (multi-select), Enter to accept. Typing a number still works, and the numbered prompts remain the fallback (plain text mode, piped input, a list taller than the terminal, or any terminal error).
- Optional automatic security updates. The setup script offers (once, default yes) to install `unattended-upgrades`, enable the daily run (`/etc/apt/apt.conf.d/20auto-upgrades`), and add the Raspberry Pi and Raspbian package archives, and Cloudflare's `cloudflared` repository, plus an optional 04:00 automatic restart (`/etc/apt/apt.conf.d/52rwsols-auto-updates`). `python3 setup.py --auto-updates` runs only this step. Nothing is asked or changed when automatic updates are already on.
- Cloudflare DNS check before the remote access mode question. The wizard explains that Cloudflare Tunnel and Access need a domain whose DNS is managed by Cloudflare, and that the way the domain's IP is updated (ddclient, router, other, none) does not matter. It looks up the nameservers of the saved tunnel hostname and the ddclient names (public DNS over HTTPS, no token), and asks for a domain only when none of them is on Cloudflare. When no domain qualifies, the Cloudflare Tunnel option is left out and the wizard says it is skipping the Cloudflare Tunnel and Access options and why. A failed lookup, or an install already in Tunnel mode, keeps the option. The tunnel hostname prompt rejects names in a zone that is not on Cloudflare.
- The automatic Tunnel setup offers to reuse the Cloudflare API token that ddclient already has for dynamic DNS (`protocol=cloudflare`, `login=token`). The wizard checks with read-only API calls that the token can see the zone, the account's tunnels and, when Access is enabled, Access applications; when the check fails it lists what is missing and offers to check again after you add the permission in the Cloudflare dashboard (no restart), or to take a pasted token as before. The dynamic DNS step of setup now notes the extra permissions when you create a Cloudflare token there. The token is read through sudo, kept in memory and never printed. `CLOUDFLARE_API_TOKEN` still takes priority.
- The API token step prints a Cloudflare token template link that opens the Create Token page with a suggested name (`RWSOLS setup (<hostname>)`) and the permissions pre-filled. The permission list shows only what the chosen options need (the Access permissions only with Access, the service token permission only when a service token was requested). A pasted token is checked with read-only calls before anything is changed; when something is missing the wizard lists it and offers to check again, take another token, or continue.
- The service token question now explains what a service token is, gives an example, and says that most people should answer No (still the default).
- The setup script is now a checklist of seven sections (base install, remote access, dynamic DNS, HTTPS on your LAN, hostname allowlist, security updates, passphrase and computers). It shows what is done and what is left, continues where an earlier run stopped, and can run any one section again. Existing installs are recorded as complete. The passphrase and the `config.php` editor moved to the last section, and opening the editor is now a question.
- The setup script asks for your computers one at a time (name, MAC address, IP address) and writes them to `config.php`, so the file no longer has to be edited by hand. A list that is already filled in is shown and kept unless you choose to add, remove or start over. The sleep command, sleep port and ping timing can be changed the same way. Opening the file in nano afterwards is optional.
- The setup script hands the passphrase to PHP on standard input when hashing it. A passphrase containing a quote character used to break the hashing command, and the passphrase was briefly visible in the process list.
- The tunnel questions say what the domain and the tunnel hostname are each used for, show which name is being looked up, and confirm that the chosen hostname's DNS is on Cloudflare.
- Dynamic DNS is its own section, independent of the remote access mode: required for port forwarding, optional for LAN only and Cloudflare Tunnel (for people who want a domain to keep following their home IP for other services). An existing ddclient setup can be kept, redone or turned off.
- The HTTPS section explains that a Cloudflare Tunnel hostname already has a trusted certificate and that the port 80 Let's Encrypt certificate is not needed in Tunnel mode. New option for LAN only and Tunnel modes: a trusted Let's Encrypt certificate for a LAN name inside a Cloudflare-hosted domain, using a DNS challenge (certbot's Cloudflare plugin). The DNS-only API token it needs for renewals is stored in `/etc/letsencrypt/rwsols-cloudflare.ini`, readable only by root; the dynamic DNS token can be reused. Switching to another choice removes the certificate and the stored token.
- Login throttling (`$LOGIN_MAX_ATTEMPTS`, default 5, and `$LOGIN_LOCKOUT_SECONDS`, default 900). Wrong passphrases are counted per client address (IPv6 per /64; the visitor address reported by Cloudflare for tunnel requests). A locked out client gets HTTP 429 with `Retry-After`, and the lockout is written to syslog (tag `rwsols`).
- Wiki pages: Remote Access with Cloudflare Tunnel, Adding Cloudflare Access (optional), Configuration Reference and Security.

### Changed
- **Applies to existing installs:** login throttling is on by default, also for a `config.php` without the new settings. Set `$LOGIN_MAX_ATTEMPTS = 0;` to turn it off.
- **Applies to existing installs:** the setup script sets `/var/www/html/config.php` to `root:www-data`, mode 640 (it was world-readable), and makes the `/var/www/html_backup_*` folders root-only. The web root comparison now runs through `sudo diff`.
- Re-running the setup script may ask one more question before the mode question (a domain to check against Cloudflare) when your dynamic DNS names are not on Cloudflare. Leaving it blank continues as before.
- The allowlist no longer silently drops dynamic DNS names outside Port forwarding mode. They are listed, unticked, with a note that they are only needed while router port forwards still point at the Pi. The LAN IP is no longer a separate yes/no question; it is an unticked option in the multi-select unless it was already on your list.
- The setup script now asks how RWSOLS will be reached from outside the LAN before the DDNS steps. DDNS, public IP and port 80/443 checks only run in Port forwarding mode. In the other modes the script asks for the LAN name of the Pi and the LAN encryption choice instead.
- Setup logic for remote access lives in a new `rwsols_setup` Python package used by `setup.py`.
- When the request arrives through the tunnel listener, `index.php` does not redirect to HTTPS on its own (Cloudflare terminates TLS), and builds its default redirect with `https://`.

### Security
- Host allowlist protects against DNS rebinding. Matching is exact and case-insensitive; the port and one trailing dot are ignored; there are no wildcards; a missing Host header is rejected. Apache still completes the TLS handshake for an unlisted or missing SNI name; the HTTP request that follows is rejected.
- With Cloudflare Access enabled, requests for the tunnel hostname (or arriving on the tunnel listener) must carry a valid `Cf-Access-Jwt-Assertion` token, verified in PHP (RS256, signing keys from the team's `/cdn-cgi/access/certs`, audience, issuer and expiry checked). Verification fails closed, including when the signing keys cannot be fetched. Setting only one of `$ACCESS_TEAM_DOMAIN` and `$ACCESS_AUD` denies all tunnel requests.
- The identity from a verified Access token is written to syslog (tag `rwsols`) for POST actions.
- Tunnel mode needs no inbound router ports.
